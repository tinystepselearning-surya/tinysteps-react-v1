## 1. Purpose

This audit resolves how Tiny Steps should carry existing people, learners and relationship references into the School OS identity model without breaking current Firebase Authentication, scheduling, enrollment, parent, teacher or school workflows.

The canonical target remains:

```text
Person
AuthIdentity
RoleAssignment
LearnerProfile
GuardianRelationship
TeachingAssignment
OrganisationMembership
```

This document records what the repository currently proves and which conclusions still require a read-only production-data check.

## 3. Verified current identity topology

### 3.1 Auth-backed users

Current admin user creation deliberately creates:

```text
Firebase Auth user
      │ uid
      ▼
users/{uid}
```

The user document stores both `uid` and `userId` with the same Firebase UID value.

Role-specific mirrors use the same document ID:

```text
users/{uid}
teachers/{uid}
parents/{uid}
learningPartners/{uid}
admins/{uid}
```

depending on role.

Therefore, today the **identifier value is intentionally shared** across Auth, the user profile and role mirrors.

That is an implementation fact, not a future architecture requirement.

### 3.2 Parents

A parent is currently represented by:

- Firebase Auth identity;
- `users/{uid}`;
- normally `parents/{uid}`;
- child references in `users.childIds[]`;
- learner-side fields such as `parentId`, `parentIds[]` and `primaryParentId`;
- enrollment/session parent references.

This is duplicate relationship authority.

### 3.3 Teachers

A teacher is currently represented by:

- Firebase Auth identity;
- `users/{uid}`;
- normally `teachers/{uid}`;
- operational `teacherId` references;
- historical aliases such as:
  - `teacherIds[]`
  - `assignedTeacherId`
  - `primaryTeacherId`
  - `teacherUid`
  - `teacher_id`

The existing teacher identity helpers explicitly define **`teacherId` as canonical for new operational writes** and keep the other fields for legacy/history compatibility.

### 3.4 Learners

The current primary learner creation path, `adminCreateStudent`, creates:

```text
kids/{autoGeneratedKidId}
```

and adds that ID to the parent user's `childIds[]`.

Learners are explicitly **not Firebase Auth users**.

A legacy callable also exists that creates:

```text
parents/{parentId}/students/{studentId}
```

with a separate auto-generated student ID.

The repository also uses a root `students/{id}` namespace for learner-scoped progress/projection data. Current projection compatibility code can inspect:

- `kids/{id}`
- `students/{id}`
- `parents/{parentId}/students/{id}`

and collects legacy learner aliases such as `kidId`, `studentId`, `studentUid`, `childId` and `linkedStudentId`.

Therefore `students` cannot be treated as a second canonical learner identity source without reconciliation.

### 3.5 Enrollment learner references

Existing enrollment hardening already moves toward these operational canonical fields:

```text
kidId
parentId
teacherId
```

while maintaining compatibility arrays/aliases such as:

```text
kidIds[]
studentId
parentIds[]
teacherIds[]
```

The existing canonical backfill refuses ambiguous states such as:

- `kidId != studentId`;
- canonical `kidId` absent with multiple `kidIds[]`;
- canonical parent absent with multiple `parentIds[]`;
- canonical teacher absent with multiple `teacherIds[]`.

This is useful migration precedent and should be preserved.

### 3.6 School memberships

`schoolUsers/{userId}` uses the user identifier as the document ID and contains:

```text
schoolIds[]
primarySchoolId
role = schoolAdmin
```

This is a functioning access model but conceptually maps to:

```text
OrganisationMembership
+
RoleAssignment
```

rather than permanent array-based relationship authority.

## 4. Identity decisions

### D1 — Existing auth-backed Person IDs

**Decision: preserve the existing `users` document-ID value for existing people if the live audit confirms 1:1 consistency.**

For existing auth-backed users:

```text
existing users/{currentDocumentId}
          │
          └── candidate Person.id = same opaque value
```

However, the new model must explicitly create/separate:

```text
AuthIdentity
  provider = firebase
  providerSubject = current Firebase UID
  personId = Person.id
```

The fact that an existing `Person.id` value originally came from Firebase UID becomes historical provenance only.

**Future rule:** new Person IDs must be generated by Tiny Steps identity infrastructure and must not be derived from Firebase UID, email or phone.

If a user's authentication provider/UID later changes, the Person ID remains unchanged and only AuthIdentity changes.

This decision avoids unnecessary ID churn while ending semantic coupling to Firebase Authentication.

### D2 — Canonical learner ID

**Decision: `kids/{kidId}` is the canonical learner identity candidate.**

For existing learners, the `kids` document ID should be preserved as the Person/LearnerProfile identifier wherever live references confirm that mapping.

Root `students/{id}` and nested `parents/{parentId}/students/{id}` are not permitted to become independent competing Person authorities.

They must be classified per record as one of:

- learner-scoped projection keyed by canonical kid ID;
- compatibility mirror;
- legacy learner requiring explicit link to a kid ID;
- unresolved exception requiring manual review.

No learner records are merged or deleted in Wave 0.

### D3 — Role mirrors

`parents/{uid}`, `teachers/{uid}`, `learningPartners/{uid}` and `admins/{uid}` are role-specific profile/mirror records.

They are **not separate Person identities**.

Their current shared ID values should be preserved where valid, but their ownership becomes:

```text
Person
  +
RoleAssignment
  +
role-specific profile / engagement
```

### D4 — Guardian authority

The future authoritative parent/learner relationship is:

```text
GuardianRelationship
```

The following become compatibility/projection fields during migration:

- `users.childIds[]`;
- `kids.parentId`;
- `kids.parentIds[]`;
- `kids.primaryParentId`;
- parent references embedded in operational aggregates where they are not required historical snapshots.

They must not be deleted until read/write cutover and reconciliation are complete.

### D5 — Teacher authority

The existing operational convention that **`teacherId` wins over teacher alias fields** is retained.

Legacy fields remain compatibility-only:

- `teacherIds[]`
- `assignedTeacherId`
- `primaryTeacherId`
- `teacherUid`
- `teacher_id`

The target relationship model still distinguishes:

```text
Person / FacultyProfile
TeachingAssignment
SessionStaff
```

A learner-level/default teacher and a course/enrollment-specific teacher must not be silently treated as the same relationship scope.

### D6 — School access

Existing `schoolUsers` user and school ID values should be preserved where valid.

Authority migrates from arrays to:

```text
OrganisationMembership
RoleAssignment
```

with `primarySchoolId` retained only as preference/convenience metadata if still required.

### D7 — assignedKids

Repository search shows `users.assignedKids[]` in the User model and security-rule tests but no active production relationship workflow was found that should make it authoritative.

Treat it as **legacy compatibility** unless the live audit or a later workflow audit proves an active owner.

## 5. Read-only production audit

Run locally from the repository:

```bash
npm run audit:identity-references
```

The script reads only identity/reference fields from:

- `users`
- `parents`
- `teachers`
- `learningPartners`
- `admins`
- `kids`
- root `students`
- nested `parents/*/students/*`
- `enrollments`
- `classSessions`
- `schoolUsers`
- `schools`
- `demoSessions`

It deliberately does **not** select names, email addresses, phone numbers, notes or financial fields.

The report is written under:

```text
reports/identity-reference-audit.json
```

The repository already ignores `reports/`.

Raw document IDs are not written into issue samples. Samples use short SHA-256 tokens so records can be correlated between issue categories without committing identity values.

### Credential posture

Use Application Default Credentials or an already configured `GOOGLE_APPLICATION_CREDENTIALS` environment.

Do **not** add a Firebase service-account JSON file to the repository.

The audit performs no `set`, `update`, `delete`, batch or transaction writes.

## 6. What the live audit must prove

Before the Identity & References work package is marked complete:

1. **Auth-backed identity**
   - `users/{id}` is consistent with populated `uid`/`userId`;
   - parent/teacher/LP/admin mirrors resolve to the same user;
   - role mirrors do not create competing person identities.

2. **Learners**
   - active operational learner references resolve to `kids` or have an explicit compatibility mapping;
   - every meaningful root/nested `students` record is classified;
   - any same-ID or cross-ID overlaps are understood;
   - no ambiguous duplicate learner is silently merged.

3. **Guardians**
   - parent references resolve to an auth-backed parent where expected;
   - `users.childIds[]` drift is measured;
   - `parentId`, `parentIds[]`, `primaryParentId` disagreements are enumerated.

4. **Teachers**
   - canonical `teacherId` references resolve;
   - legacy alias mismatches are measured;
   - role mirrors and operational IDs are consistent.

5. **Schools**
   - every `schoolUsers` user exists;
   - every referenced school exists;
   - primary-school references are included in membership scope.

6. **Operational references**
   - enrollment and class-session orphan references are identified;
   - ambiguities are either zero or explicitly registered as migration exceptions.

These results support preserving current opaque user document-ID values for existing Person IDs and preserving current `kids` IDs for learner identity.

### 7.2 Current-state exceptions requiring explicit review before Wave 1

The audit identified a small set of current canonical/reference problems:

1. **One active enrollment references a learner ID that no longer resolves to a current `kids` document.**
2. **Two active kids reference a teacher ID that does not resolve to a current user/teacher mirror.**
3. **One active enrollment references a teacher ID that does not resolve to a current user/teacher mirror.**
4. **Two demo-session teacher references do not resolve to current teacher identity; these require workflow/status review.**
5. **Two active `learningPartners` mirror documents have no matching `users` document.**
6. **One active admin-role user has no matching `admins` mirror.**

These are bounded exceptions; they do not invalidate the canonical ID strategy.

### 7.3 Historical/compatibility debt

The audit also found historical reference debt that is not equivalent to current identity corruption:

- 161 `classSessions` reference enrollment IDs that no longer exist — **all are past-dated**.
- 460 unresolved learner alias references in `classSessions` — **all are past-dated**.
- 214 missing parent-user/mirror references in `classSessions` — **all are past-dated**.
- 353 missing teacher-user/mirror references in `classSessions` — **all are past-dated**.
- 130 teacher alias mismatches occur on past sessions.
- 107 teacher alias mismatches occur on future sessions.

For future sessions, the audit found **no future missing teacher identity targets**. The 107 future cases are stale/mismatched legacy teacher aliases while canonical `teacherId` remains present. They are compatibility debt and must not override canonical ownership.

### 7.4 Enrollment historical exceptions

Four enrollments reference learner IDs that do not resolve to current `kids` documents:

- 1 active;
- 3 archived.

Four enrollments reference teacher IDs that do not resolve to current teacher identity:

- 1 active;
- 3 archived.

The active records must be resolved before Wave 1 writes begin. Archived records may be preserved as bounded migration exceptions if historical semantics are intentionally retained.

### 7.5 Decision from the live audit

The identity strategy is now supported by production evidence:

```text
Existing auth-backed people:
preserve current users/{documentId} value as Person.id
+
separate Firebase UID into AuthIdentity

Learners:
preserve kids/{kidId} as canonical learner identity

Parents / teachers / LPs / admins:
role mirrors, not independent Person identities

students namespaces:
currently empty in production and therefore not competing identity authorities
```

Wave 1 identity migration must first resolve or formally register the bounded current-state exceptions above.
