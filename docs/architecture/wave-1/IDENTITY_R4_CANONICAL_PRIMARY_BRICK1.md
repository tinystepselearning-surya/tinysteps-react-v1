# Wave 1 — R4 Brick 1: Canonical-Primary Learner Write Contract

**Lifecycle stage:** R4 — canonical-primary create/update paths  
**Brick:** 1  
**Scope:** learner creation contract only  
**Production behavior change:** none  
**Production writes enabled by this brick:** none

## Why R4 starts with learners

The Wave 0 identity contract requires new auth-backed Person IDs to be generated by Tiny Steps and not derived from Firebase UID, email or phone.

Current auth-backed user creation still assumes:

~~~text
Firebase UID
  = users document ID
  = role-profile document ID
~~~

That path cannot be made canonical-primary safely until the compatibility/read contract for UID-decoupled people is explicit.

Learner creation does not have that problem.

Current learner IDs are already generated independently of Firebase Authentication. The existing `kids/{kidId}` identifier can therefore become the canonical learner Person ID without violating the frozen identity decisions.

R4 intentionally starts there.

## Permanent canonical write contract

The planner is:

~~~text
functions/src/schoolOS/identity/canonicalPrimaryPlanner.ts
~~~

For a new learner, the permanent canonical plan is:

~~~text
people/{personId}
learnerProfiles/{personId}
guardianRelationships/{deterministicRelationshipId}
learnerDetails/{personId}
learnerReadModels/{personId}      # only when an initial summary exists
~~~

All canonical documents carry:

~~~text
schemaVersion
createdBy
updatedBy
canonicalAuthority = {
  schemaVersion,
  authority = canonical-primary,
  command = learner_create,
  writeId
}
~~~

They deliberately do **not** carry Wave 1 migration provenance. New canonical records are live product writes, not historical backfill artifacts.

## Compatibility projections

Until R5 readers and rules are cut over, current legacy surfaces still need:

~~~text
kids/{personId}
users/{parentId}.childIds[]
~~~

The planned `kids` document is explicitly marked as a compatibility projection:

~~~text
_wave1CanonicalProjection = {
  schemaVersion,
  authority = canonical-primary,
  command = learner_create,
  writeId,
  canonicalPersonId
}
~~~

The write ID is designed so the legacy-sync bridge can later distinguish a canonical-origin projection transition from a genuine legacy-side edit.

This brick defines that detection helper but does not wire it into the production trigger yet.

## Canonical facts preserved

The learner plan keeps the existing business facts while assigning permanent ownership:

| Fact | Canonical destination |
|---|---|
| learner display name | `people` |
| learner status | `people` + `learnerProfiles` |
| learner age | `learnerProfiles.ageYears` |
| grade | `learnerDetails.grade` |
| parent/guardian link | `guardianRelationships` |
| initial summary snapshot | `learnerReadModels.summary` |
| legacy learner shape | `kids` compatibility projection |
| parent child backlink | `users.childIds[]` compatibility projection |

## Safety properties

Brick 1 is contract-only.

It does not modify:

- `adminCreateStudent`;
- `kidsService`;
- Student Management browser writes;
- the legacy identity sync trigger;
- Firestore Security Rules;
- readers;
- existing production documents.

Therefore:

~~~text
canonicalPrimaryWrites = false
legacyWritesFrozen = false
readerCutoverAuthorized = false
securityRulesCutoverAuthorized = false
destructiveDeletionAuthorized = false
~~~

## Validation

Regression tests:

~~~text
functions/test/canonicalPrimaryPlanner.spec.ts
~~~

They verify:

1. canonical learner targets are deterministic;
2. canonical records use canonical-primary ownership rather than migration ownership;
3. the compatibility `kids` projection is explicitly marked;
4. the parent backlink is planned as a compatibility array-union;
5. a Tiny Steps learner ID is independent of Firebase UID;
6. compatibility write-ID transitions can be distinguished from later legacy edits;
7. invalid canonical inputs fail closed.

## Next brick

R4 Brick 2 may wire the server-side learner creation command only after it can atomically:

1. validate the canonical parent identity;
2. create the canonical learner documents;
3. write the compatibility `kids` projection;
4. write the compatibility parent backlink;
5. prevent the legacy-sync trigger from treating that canonical-origin projection as a new legacy authority;
6. verify post-write canonical/compatibility parity.

Browser-side learner update writers remain legacy-authoritative until their own R4 migration.

No auth-backed user writer should be switched until the UID-to-Person compatibility contract is explicit.
