# Wave 1 — R4 Brick 2: Canonical-Primary Admin Learner Creation

**Lifecycle stage:** R4 — canonical-primary create/update paths  
**Brick:** 2  
**Production entry point:** `adminCreateStudent`  
**Reader cutover:** no  
**Security Rules cutover:** no  
**Legacy write freeze:** no  
**Destructive retirement:** no

## Purpose

Brick 2 converts the existing server-side Admin learner-creation path from legacy-first creation to canonical-primary creation while preserving every compatibility surface still needed before R5.

The affected callable remains:

~~~text
adminCreateStudent
~~~

The UI contract remains compatible:

~~~text

fullName
ageYears
grade
status?
countryCode?

response:
success
kidId
parentId
fullName
message
timestamp
~~~

Brick 2 adds a non-breaking response field:

~~~text
consistencyVerified
~~~

## Canonical identity generation

A new learner Person ID is generated from the canonical `people` namespace:

~~~text
people/{newRandomId}
~~~

The same opaque ID is then used for the learner's canonical profile and temporary compatibility projection.

The ID is therefore:

- generated by Tiny Steps infrastructure;
- independent of Firebase Auth UID;
- independent of email;
- independent of phone;
- independent of parent identity;
- reusable as the permanent learner Person ID.

## Canonical parent gate

Creation no longer treats the legacy `users` role field as parent authority.

The transaction requires:

~~~text
people/{parentId}
  personId == parentId
  kind == adult
  status == active

roleAssignments/{deterministic parent role ID}
  personId == parentId
  role == parent
  scopeType == global
  scopeId == null
  status == active
~~~

The existing `users/{parentId}` document must still exist because it remains a compatibility projection and still receives `childIds`.

This is an intentional transitional split:

~~~text
canonical collections = parent authority
users              = compatibility destination
~~~

## Atomic write set

One Firestore transaction validates the parent and collision conditions, then writes the full learner create set.

Canonical writes:

~~~text
people/{personId}
learnerProfiles/{personId}
guardianRelationships/{relationshipId}
learnerDetails/{personId}
learnerReadModels/{personId}
~~~

Compatibility writes:

~~~text
kids/{personId}
users/{parentId}.childIds += personId
~~~

The initial learner summary remains behavior-compatible with the old Admin path:

~~~text
phonicsMastery = 0
grammarMastery = 0
speakingMastery = 0
attendanceRate30d = 0
creditsRemaining = 0
~~~

## Ownership

New canonical records carry:

~~~text
canonicalAuthority = {
  schemaVersion: 1,
  authority: canonical-primary,
  command: learner_create,
  writeId
}
~~~

They do not receive Wave 1 migration provenance.

The `kids` compatibility document carries:

~~~text
_wave1CanonicalProjection = {
  schemaVersion: 1,
  authority: canonical-primary,
  command: learner_create,
  writeId,
  canonicalPersonId
}
~~~

## Legacy-sync loop suppression

The existing `kids` legacy-sync bridge remains active because other writers have not yet been migrated.

Brick 2 changes its decision gate so a marker is only a hint. Suppression also requires canonical corroboration:

~~~text
new canonical projection write ID
+ kids marker canonicalPersonId == source ID
+ people/{sourceId}.canonicalAuthority.writeId == marker.writeId
+ matching canonical-primary learner_create authority
→ do not treat the kids write as legacy authority
→ do not rewrite canonical state with migration ownership
~~~

A marker transition performs one canonical `people/{sourceId}` point read for this corroboration. It does not add reads to ordinary legacy updates.

If the marker is forged or does not match canonical authority:

~~~text
identity fields changed
→ continue into legacy reconciliation
→ existing canonical ownership guard prevents overwrite

only marker changed
→ no identity reconciliation is needed
~~~

And:

~~~text
same projection write ID + later legacy identity-field edit
→ treat as a real legacy edit
→ run compatibility reconciliation
~~~

This prevents canonical → legacy → canonical feedback loops without trusting a client-editable marker or hiding genuine remaining legacy writes.

The parent `users.childIds` compatibility update does not trigger canonical identity work because `childIds` is already outside the legacy-sync identity projection.

## Duplicate-name behavior

The existing Admin UX rule is retained:

~~~text
same normalized child name under the same parent
→ already-exists
~~~

Until R5 reader cutover, this duplicate check still queries the `kids` compatibility collection. It is a UX duplication check, not identity authority.

## Collision guards

Before writing, the transaction rejects:

- a generated learner ID that collides with `users/{id}`;
- any existing canonical target at the generated Person ID;
- any existing `kids/{personId}` compatibility target.

The canonical and compatibility creates use transaction `create` semantics rather than merge semantics.

## Bounded post-write verification

After the atomic commit, the callable performs one bounded verification pass over the newly created canonical and compatibility records.

It verifies:

- every planned canonical field;
- the `kids` compatibility projection;
- the parent `childIds` backlink.

There is no polling loop and no recurring Firestore read path.

A mismatch is logged through:

~~~text
wave1_canonical_primary_learner_write
~~~

The callable does not retry the create after a committed write, avoiding duplicate learner creation.

## Telemetry privacy

Canonical learner creation telemetry never emits raw learner, parent, actor or write identifiers.

All identity-bearing telemetry values are deterministic SHA-256 privacy tokens truncated to 24 hexadecimal characters and namespaced by subject type.

The Admin callable also omits learner names from success and error logs.

Therefore:

~~~text
rawIdentityIdsInTelemetry = false
rawLearnerNamesInTelemetry = false
firestoreTelemetryWrites = 0
~~~

## Error compatibility

The callable preserves the important existing client-visible errors:

- missing selected parent → `not-found`;
- invalid/inactive canonical parent identity → `failed-precondition`;
- duplicate student name → `already-exists`;
- generated identity collision → `aborted`;
- unexpected server failure → `internal`.

## Explicitly not cut over

Brick 2 does not change:

- `createStudentForParent`;
- browser-side `kidsService` creation/update;
- Student Management browser update writers;
- auth-backed user creation;
- school creation;
- readers;
- Firestore Security Rules;
- legacy write freeze;
- destructive retirement.

Therefore R4 remains incomplete after Brick 2.
