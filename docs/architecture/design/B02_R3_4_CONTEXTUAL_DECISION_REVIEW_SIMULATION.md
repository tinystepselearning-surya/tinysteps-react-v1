## Simulation scope

Eight representative explicit role/action/scope combinations from the 15 proposed R3.3 entries: online session attendance, online teaching view, campus teaching view, physical daily attendance, guardian view, finance view, partner reader view, partner operator view. Seven remaining combinations (institution creation, campus creation, two roster scopes, finance posting, partner management, scoped support) are intentionally not modeled and default to would-deny. No live existing right is removed. The prototype repeats the reviewed candidate vocabulary in a separate synthetic matrix to avoid dependency on unmerged code; a single approved policy catalogue must replace this duplication before integration. Proposed resource kinds, purposes and field labels are fixture vocabulary only, not existing record fields, approved schemas or final field policies.

- Request: action, exact resource ID, tenant/organisation/optional campus scope, purpose and bounded requested field list. No actor identity, grant, membership or allow flag accepted from request.
- Independent test harness provides a synthetic current time and revision fence separately from evidence. Evidence: principal (person/auth status), tenant, organisation, campus or null, tenant membership, organisation membership, grant, resource and action-specific relationship. Match all subject/owner/target/scope identifiers, active status, exact same-generation revision, and same-tick observation. Membership/grant/relationship use explicit finite half-open intervals; missing/null endpoints deny in this limited simulation. No inferred parent/household/payer rights; require exact relationship evidence. Field list nonempty, distinct and bounded, exact proposed purpose and allowlist. Unknown or malformed input yields fixed reason code. Outputs would-allow / would-deny with productionAuthorization:false; no real access decision, side effects or personal data.
- The evidence and fence are artificial DTOs, not authenticated credentials, independently fetched facts, revocation guarantees or authorization assertions. The relationship classification abstracts the eventual domain-specific checks (including guardian custody/consent, staff assignment, school register/placement, provider and finance scope); it does not implement those source queries. No real trusted evidence provider, transaction recheck, clock authority, distributed revision scheme, report watermark verification, multi-grant combination, role assignment writer, Rules, storage, migration or SDK integration. Same-tick requirement is a conservative fixture rule, not a production TTL or proposed requirement for all persisted records.
- Correct prior illustrative R3 design budget: an organisation/campus-scoped action needs both TMB and MEM when both are required. A naive campus path with separate current fence and all nine logical evidence rows is ten point lookups (principal + fence + TEN + ORG + CAM + TMB + MEM + grant + resource + relation); online omits CAM. This is a conceptual count only, not measured billed reads or a fixed production budget. Actual domain relationship may require several records. Optimize via reviewed authoritative context reuse/co-located version fences without weakening current revocation. No runtime reads incurred by simulation. Premium direct 1:1 requires no group/campus; nonurgent T-1 reports never authorize access.
