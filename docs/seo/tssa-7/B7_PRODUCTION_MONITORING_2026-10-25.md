## 1. Baseline and discovered reliability gap

A rolling, hourly production-origin standards audit **already exists**:

- [Hourly readiness workflow](../../.github/workflows/rolling-public-seo-health.yml) (repository-relative workflow path is in GitHub root).
- Source verifier `scripts/seo/rolling_public_health.py` and an isolated persistent `seo-url-health-tracker` branch: `MASTER_URL_TRACKER.csv`, `LATEST_SUMMARY.md`, `CHANGES.md`.
- 202 selected public URLs from static/blog/course/parent XML sitemaps, 10 per slot for the first 19 slots, 12 in slot 20, then catch-up. Each live response checks HTTP status, final URL, self-canonical, X-Robots and HTML robots, visible title/description/H1/text, valid JSON-LD syntax, public sitemap inclusion and robots.txt rules for Googlebot/Bingbot/OAI-SearchBot. Site failures versus unverified transport/crawl state are separated.
- The prior hourly schedule uses minute 53 UTC (IST :23) and may be delayed or skipped by GitHub. It cannot guarantee 24 uninterrupted successful runs or provider-selected indexing.
- The tracker snapshot fetched from GitHub at the beginning of this B7 work was generated **25 October 07:18 IST** and recorded only **20 of 202** URLs checked so far that day (20 PASS; zero observed WARN/FAIL/UNVERIFIED; 182 unchecked). **This is not a website failure** and the current day may gain coverage later.

**Identified gap:** slots 21 and 22 previously did nothing, and slots 23 and 24 could cover at most 20 missed URLs. A delayed/skipped scheduled run could leave a substantial portion of the daily set unobserved while headlines still announced a clean observed cohort.

## 2. B7 implementation

**A. Allow all four final daily slots to recheck uncovered work:** hourly script accepts slots **21–24** as ten-URL retry batches; its existing CI expectations now assert `21:10` and `22:10` rather than `21:0` and `22:0`. A fixed daily 202-URL baseline and source drift are still validated in the hourly job. This is a conservative 20-more-URL recovery capacity, not a guarantee against larger GitHub schedule outages.

**B. Add independent evidence reconciliation:** `scripts/seo/tssa7_b7_monitor.py` reads the persistent 202-URL tracker, its upstream summary, the current GitHub Hosting production marker SHA and B6 historical evidence generated by `scripts/tssa7-b6-native-benchmark.mjs`. It emits `artifacts/tssa7-b7/B7_STATUS.json` and `B7_STATUS.md`. Its checks:

- Require 202 unique public-origin URL/index rows and known statuses;
- Count **only observations actually recorded on the current IST date** with valid non-future timestamps, never stale yesterday-PASS as fresh;
- Distinguish live technical FAIL, WARN, UNVERIFIED, monitoring sample staleness, incomplete coverage and healthy checked pages;
- Escalate a **confirmed technical FAIL** immediately; escalate **unfinished 202-URL coverage after 21:00 IST** or >3-hour absence of samples at that point as a **monitoring** failure, not an origin outage;
- Record the existing Hosting marker as historical verified-release provenance, explicitly **not** a fresh live build identity check or deployment;
- Reconcile the existing B6 historical 36 native answers and disclose **zero freshly performed native provider sessions**, Bing's zero *tested* denominator and external provider dependency. Never infer citation success or Google/Bing selection from technical checks.

**C. Add persistent heartbeat and actionable alert route:** `.github/workflows/tssa7-b7-production-monitoring.yml` runs on PR/dispatch and schedules two daily checks, approximately **08:17 and 21:17 IST**. It records results as retained GitHub Actions artifacts and, for **scheduled** runs with genuine technical FAIL or post-cutoff monitoring coverage/staleness gaps, posts a dated evidence-backed exception comment to **issue #772**. Pull-request checks never post alerts. Separate jobs grant `issues:write` permission only to the scheduled notification job; monitoring checks remain read-only.

GitHub schedules are best-effort. The issue notification cannot run if GitHub fails to execute the scheduled workflow at all. Staleness is therefore a measured residual risk, not a guarantee of 100% alert delivery.

**D. Regression validation:** `scripts/seo/test_tssa7_b7_monitor.py` guards missing coverage, morning incomplete-but-not-late state, real FAIL, UNVERIFIED vs site failure, stale timestamps, duplicate URLs, fabricated Bing success and prior-day status leakage. B7 workflow additionally exercises the hourly source runner's 1, 19, 20, 21–24 dry-run slot-selection boundaries and the existing B6 historical audit. Source code and the independent health-data branch are not overwritten by B7.

## 3. Release and production evidence boundaries

Last verified website Hosting release before B7 was B5 [deploy #40136664359](https://github.com/tinystepselearning-surya/tinysteps-react-v1/actions/runs/40136664359) at `cc41829719981c57a071ff60e25974f8633a307e` with live build identity and origin integrity accepted. Later B6 and roadmap updates correctly skipped Hosting deployment.

This B7 work only changes GitHub workflows, a read-only source monitor and its tests, plus one conservative catch-up selection in the existing monitoring script. It should **not** trigger production Hosting or Functions deployment. Check the post-merge Actions run and Hosting marker before saying that is verified.

**Evidence boundaries:**

- A technical PASS does not establish **Google indexed-state, selected canonical, Bing indexed-state, current ranking, ChatGPT citation or Gemini citation**.
- B6's 19 October native sessions are historical. A fresh four-product 48-cell benchmark was **not executed** in this engineering run, and Bing/Copilot's twelve intended sessions remain **NOT_TESTED**, not "zero citations".
- Source sitemap and checker counts may evolve; an explicitly reported source drift should trigger a reviewed baseline update rather than suppressing the check to manufacture 202/202.
- The hourly job samples actual HTTP pages. The B7 digest analyses that recorded sample set and its freshness; B7 does not independently crawl or use owner Search Console credentials.
- Actual index/provider outcomes remain separately owned by issues #747 and #772, outside the safe scope of repository-engineering closure.
